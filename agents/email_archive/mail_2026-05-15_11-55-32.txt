## Почему это "сырое мясо"?

### Пример №1 — «Баг с двойным списанием»

**Что есть:** описание бага, причина, фикс.

**Чего нет:**
- **Контекста и напряжения.** «Платежный шлюз» — само собой. А что на кону? Деньги пользователей? Репутация? Штрафы?
- **Боли читателя.** «Retry без идемпотентности» — это сухо. Где момент "я тоже так попадал"?
- **Драматургии.** Нет завязки, кульминации, развязки. Просто факты.
- **Триггера.** Почему я должен это читать? Чтобы не повторить? Чтобы вспомнить свой баг? Чтобы поржать?

**Что вместо этого нужно:** сторителлинг. «Я полез в отчёт ночью, хотел проверить одну цифру — и увидел, что три месяца подряд у нас утекали деньги. Вот как я это нашёл».

### Пример №2 — «Баг с часовым поясом»

**Та же проблема:** тема огонь, подача — техническая заметка в блокнот.

**Чего нет:** последствий для юзера, масштаба (сколько задач уехало), эмоции.

### Пример №3 — «Чек-лист POST /users»

**Здесь проблема структурная:** 
- Автор путает уровень: то ли чек-лист для стажёра, то ли провокация для сеньоров.
- «Что я пропустил?» — хороший заход, но вопросы разрозненные.
- Нет единого сценария. Откуда пользователь? Что за email? Какой age валидный?
- **Метод — не чек-лист.** Нет логики: аутентификация → авторизация → валидация → бизнес-логика → инфраструктура.

## Промт для копирайтера (которого тебе не хватало)

Вот **форматы и фактура**, которые работают для твоего канала (судя по контексту — про тестирование, QA, инженерную культуру):

### Формат 1: «Байка / кейс» (история с выводом)

```
[ТРИГГЕР] «Когда в проде баг живёт дольше, чем твой испытательный срок»
[ЗАВЯЗКА] Описание ситуации — кто, где, когда, что пошло не так
[КУЛЬМИНАЦИЯ] Как нашли — случайно, в 3 часа ночи, через отчёт
[РАЗВЯЗКА] Почему произошло — коренная причина 
[ВЫВОД] Что сделали — фикс, процесс, урок
[ВОВЛЕЧЕНИЕ] «А у вас был баг, который ...?»
```

### Формат 2: «Разбор / туториал» (от проблемы — к решению)

```
[ПРОБЛЕМА] Ситуация: пользователь жалуется, падают деньги, теряются данные
[КОРЕНЬ] Почему это произошло (технически)
[ЧТО ДЕЛАТЬ] Чек-лист / правило на будущее
[БОНУС] Неочевидный граничный случай
```

### Формат 3: «Чек-лист / провокация» (с механикой "ай, точно!")

```
[ЗАГОЛОВОК] «Что ты упускаешь при тестировании POST /users?»
[СПИСОК] 3-5 пунктов, которые очевидны
[ПРОВАЛ] А вот эти 3 пункта ты забыл — и зря
[ОБЪЯСНЕНИЕ] Почему каждый важен
[THREAD] Если хочешь полный чек-лист — 🔥
```

## Переписываю твои примеры в эти форматы

### Пост №1 (переделанный)

**«Три месяца мы теряли деньги из-за одной строчки кода»**

Платежный шлюз. Клиент оплачивает >100 000₽. Деньги списываются дважды. Три месяца никто не замечал.

Как нашёл?
Проверял отчёт за квартал. Увидел аномалию: одна и та же транзакция — дважды. Свёл платёжки — разница на миллионы.

Корень: `retry` без `idempotency key`. Повторный запрос = повторное списание.
Фикс: добавили идемпотентность за день.

Что теперь:
— Все внешние API проверяем на идемпотентность.
— В critical flow — обязательный тест «двойной запрос».

👉 **А у вас какой баг дольше всего прожил в проде?**

*#тестирование #платежи #баги*

---

### Пост №2 (переделанный)

**«Пользователь создал задачу на 15:00, а оповещение пришло в 12:00»**

CRM. Баг жил 2 недели, пока 3 клиента не позвонили в поддержку с одним вопросом: «Почему напоминания приходят раньше?»

Разбираемся:
- `created_at` хранится в UTC
- Фронтенд не конвертирует таймзону
- Пользователь в Москве (UTC+3) — видит 15:00, сервер считает 12:00

Урок: **каждый раз, когда API возвращает время, проверяй таймзону**. 
Даже если кажется, что «все в UTC».

Чек-лист для тестов:
1. Создать запись в UTC+3 → фронт показывает UTC+3
2. Создать в UTC-8 → фронт показывает UTC-8
3. Перевести часы на летнее время — не сломается?

*#тестирование #баги #время*

---

### Пост №3 (переделанный)

**«Чек-лист POST /users: 5 пунктов, которые ты пропустил»**

Начинающие тестировщики проверяют:
✅ POST с валидным телом → 201
✅ Без авторизации → 401
✅ С пустым телом → 400

Сеньоры добавляют:

1. **Дубликат email** → 409 Conflict
   — Имейл уникален? А если регистр разный? `Ivan@mail.ru` vs `ivan@mail.ru`

2. **XSS в name** → `<script>alert(1)</script>`
   — Убедись, что name не рендерится как HTML

3. **Граничные значения age**
   — age = 0 (только родился?),
   — age = 150 (долгожитель?),
   — age = -5 (отрицательный возраст)

4. **SQL-инъекция в полях**
   — name = `' OR 1=1; --`

5. **Content-Type не application/json**
   — Пришли form-data → что будет?
