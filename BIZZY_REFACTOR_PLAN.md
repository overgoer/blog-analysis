## Пересмотр приоритетов (2026-05-21)

Ранее приоритет был: #2 (SQL) → #1 (категоризатор). Теперь, когда оба сделаны, следующий шаг определён исходя из **пользы для Bizzy-стратега**:

### Следующий: #6 — База знаний продуктов (Practicum)

**Почему:** Bizzy умеет смотреть метрики и сравнивать категории. Но его советы остаются generic («пиши больше career»), потому что он **не знает продукт**. Он не может ответить на вопрос: «как этот пост приближает продажу Practicum?»

**Что даёт:**
- Bizzy перестаёт советовать «пиши то, что заходит у конкурентов»
- Начинает советовать «конкурент получает 30% на career — вот угол для поста про Practicum, который бьёт в ту же боль»
- Может объяснить, почему конкретный пост стратегически важен

**Что нужно:** информация о Practicum от пользователя (описание, ЦА, сценарии, боли, отзывы).

### Потом: #3 — Трекер подписчиков

**Почему после #6:** трекер даёт измеримый результат, но без продукта Bizzy не знает, на какую аудиторию расти. Вместе — Bizzy видит: «пост про Х дал +30 подписчиков, а пост про Y — +5. X — это про автоматизацию, а Practicum — про автоматизацию. Пиши больше X.»

### Теперь: #3 — Трекер подписчиков

Продукт есть, ЦА понятна, Bizzy знает что продавать. Теперь нужно,
чтобы он видел, работает ли стратегия. Трекер подписчиков даст ответ
на вопрос «растём или нет» не по хардкод-цифрам, а по реальным данным.

**Что сделать:** крон раз в день сохраняет subscribers_count в SQLite.
Bizzy получает инструмент `query_subscriber_trend(channel, days)`.
Через неделю данных — видит связь «этот пост дал +50 подписчиков».

### Потом: #5 — Цикл обратной связи

Только когда есть продукт (#6) и трекер (#3). Bizzy пишет «сделай Х» → через N дней проверяет метрики → корректирует.

## Контекст — почему сейчас Bizzy тупит

Текущая архитектура:

```
analyzer.py (крон) → scraper.py → SQLite
                  → insights.py (DeepSeek) → notable post analysis
                  → reporter.py → Obsidian

strategy_review.py (крон/по запросу) → читает БД → генерирует markdown + графики → Obsidian + TG

Bizzy → через tools: SQL-запросы, категоризатор, сравнение каналов
```

Проблемы:
1. ~~**Bizzy не видит данные — он видит текст.**~~ ✅ Теперь видит — SQL-инструменты работают.
2. ~~**Стек переусложнён.**~~ ⬜️ strategy_review.py всё ещё делает слишком много, но Bizzy может его игнорировать.
3. **Нет цикла обратной связи.** Bizzy предлагает стратегию → через неделю должен увидеть, сработала ли она. Сейчас не видит.
4. **Нет трекера подписчиков.** Оценить охот реально (`240 views / 1500 subs = 16%`) — нельзя динамически, только хардкод.
5. ~~**Notable-анализ галлюцинирует.**~~ ⬜️ Частично исправлено (media_type, порог вовлечения), но DeepSeek Flash всё ещё может выдумывать.
6. **Bizzy не знает продукт.** Самая большая проблема — его советы generic, потому что он не понимает, что продаётся.

---

## Целевое видение — Bizzy как драйвер продаж

Конечная цель: Bizzy понимает продукт → видит его слабые места → пишет пост, который это видение доносит → и может объяснить, почему этот пост важен в общей схеме.

Конкретно:
- **Понимание продукта:** Bizzy знает Practicum, его API-симулятор, сценарии использования, болевые точки аудитории
- **Анализ стратегии:** Bizzy сам решает, какие метрики посмотреть, и пишет выводы своими словами, а не пересказывает markdown
- **Контент с целью:** Bizzy не просто пишет пост — он пишет пост, который двигает к P0 (продажи Practicum), и может объяснить, как именно
- **Учится на результатах:** Bizzy написал "сделай X" → через N дней видит, сработало ли → корректирует

## Оценка реалистичности

План — **реалистичен на 90%**, но с оговорками:

### Что уже готово и работает:
- Скрапер каналов (11 штук, 50 постов каждый) — **работает**, данные есть
- База данных — SQLite с постами, метриками, категориями, целями
- Базовый Bizzy с function calling и контекстом
- Отправка в Telegram с универсальным markdown→HTML конвертером
- Obsidian vault для артефактов
- SQL-инструменты Bizzy для прямых запросов
- Категоризатор (темы + цели) с runtime-управлением ключевыми словами
- Кастомные метрики

### Что надо докупить / настроить:
- **База знаний продукта** — информация о Practicum
- **Трекер подписчиков** — крон + Telegram API (getChatMembersCount)

### Где план может споткнуться:

1. **Bizzy (DeepSeek v4 Flash) не станет умнее от рефакторинга.** Он останется той же моделью. Рефакторинг даёт ему *доступ* к данным и *контекст*, но качество его анализа ограничено моделью.

2. **Решение:** не пытаться сделать Bizzy супер-аналитиком на Flash. Сделать так:
   - Flash — для контента, быстрых ответов, классификации
   - Для стратегических обзоров использовать **DeepSeek Reasoning** (или Opus 4) — медленнее, дороже, но выводы глубже
   - Bizzy-Flash спрашивает Bizzy-Reasoning: "дай стратегический анализ по этим данным, я передам пользователю"

3. **Цикл обратной связи (п. 5) — ключевой, но сложный.** Bizzy должен помнить, что он советовал неделю назад, и иметь данные, чтобы проверить. Это требует:
   - Персистентного хранения рекомендаций с датами
   - Автоматической сверки с текущими метриками
   - Триггера "Bizzy, проверь свои прошлые советы"
   Без этого он будет каждый раз генерировать одно и то же.

4. **У Bizzy нет чувства времени.** Он не знает, что "неделя прошла". Ему нужен внешний триггер — крон или кто-то его пробуждает.

### Итоговая оценка: 8/10

План реален. Риски не в архитектуре, а в модели (DeepSeek Flash может не дотянуть до нужной глубины анализа) и в человеческом факторе (Bizzy нужно настраивать, кормить данными, чистить контекст).
