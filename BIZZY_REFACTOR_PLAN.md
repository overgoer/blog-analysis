# Bizzy Refactor Plan

> Статус: черновик. Дата: 2026-05-21.
> Цель: превратить Bizzy из «пишет контент по указке, но тупит в стратегии» в драйвера продаж.
> Подход: не переписывать всё сразу, а растить «щупальцами» — по одному узлу влияния за раз.

---

## Контекст — почему сейчас Bizzy тупит

Текущая архитектура:

```
analyzer.py (крон) → scraper.py → SQLite
                  → insights.py (DeepSeek) → notable post analysis
                  → reporter.py → Obsidian

strategy_review.py (крон/по запросу) → читает БД → генерирует markdown + графики → Obsidian + TG

Bizzy → через tools вызывает strategy_review.py → получает готовый markdown-текст → пережёвывает его
```

Проблемы:
1. **Bizzy не видит данные — он видит текст.** `strategy_review.py` рождает готовые выводы, а Bizzy их пересказывает. Нет инструментов для прямого запроса БД.
2. **Стек переусложнён.** `strategy_review.py` и скрапер, и аналитик, и визуализатор, и рекомендатель.
3. **Нет цикла обратной связи.** Bizzy предлагает стратегию → через неделю должен увидеть, сработала ли она. Сейчас не видит.
4. **Нет трекера подписчиков.** Оценить охот реально (`240 views / 1500 subs = 16%`) — нельзя, потому что нет данных о подписчиках.
5. **Notable-анализ галлюцинирует.** DeepSeek анализирует текст, не видя медиа. Выводы — generic-фразы, которые Bizzy потом использует как факты.

---

## Целевое видение — Bizzy как драйвер продаж

Конечная цель: Bizzy понимает продукт → видит его слабые места → пишет пост, который это видение доносит → и может объяснить, почему этот пост важен в общей схеме.

Конкретно:
- **Понимание продукта:** Bizzy знает Practicum, его API-симулятор, сценарии использования, болевые точки аудитории
- **Анализ стратегии:** Bizzy сам решает, какие метрики посмотреть, и пишет выводы своими словами, а не пересказывает markdown
- **Контент с целью:** Bizzy не просто пишет пост — он пишет пост, который двигает к P0 (продажи Practicum), и может объяснить, как именно
- **Учится на результатах:** Bizzy написал "сделай X" → через N дней видит, сработало ли → корректирует

## План — щупальца по одному

| # | Щупальце | Что даёт | Сложность | Зависимости |
|---|-----------|----------|-----------|-------------|
| 1 | **Тупой категоризатор** — чистая классификация по ключевым словам, без API. Раскладывает посты конкурентов и свои по темам, целям поста (прогрев/продажа/экспертиза/юмор) | Bizzy видит: «в какой категории я пишу, а в какой — конкуренты» | 1 день | — |
| 2 | **Bizzy → прямые SQL-инструменты** — вместо `strategy_review` добавить `get_metrics(channel, days)`, `get_top_posts(channel, n)`, `get_category_distribution(channel)` | Bizzy сам выбирает, что посмотреть, а не пережёвывает готовый текст | 1 день | #1 |

## Оценка реалистичности

План — **реалистичен на 90%**, но с оговорками:

### Что уже готово и работает:
- Скрапер каналов (11 штук, 50 постов каждый) — **работает**, данные есть
- База данных — SQLite с постами, метриками, категориями
- Базовый Bizzy с function calling и контекстом
- Отправка в Telegram
- Obsidian vault для артефактов
- Анализатор форматов / best day / time / engagement quality — уже в коде

### Что надо докупить / настроить:
- **Трекер подписчиков** — tdl не даёт `members_count` в `chat ls`, придётся через Telegram API напрямую (`getChatMembersCount`), либо парсить `tdl chat ls --raw`
- **Bizzy с прямым SQL** — это самое простое: три функции + три SQL-запроса

### Где план может споткнуться:

1. **Bizzy (DeepSeek v4 Flash) не станет умнее от рефакторинга.** Он останется той же моделью. Рефакторинг даёт ему *доступ* к данным и *контекст*, но качество его анализа ограничено моделью. Если модель неспособна к многошаговым рассуждениям о стратегии — никакой рефакторинг не поможет. **DeepSeek v4 Flash** — быстрая лёгкая модель, она хороша для контента и простых вопросов, но для глубокой стратегии ей может не хватать "думания".

2. **Решение:** не пытаться сделать Bizzy супер-аналитиком на Flash. Сделать так:
   - Flash — для контента, быстрых ответов, классификации
   - Для стратегических обзоров использовать **DeepSeek Reasoning** (или Opus 4) — медленнее, дороже, но выводы глубже
   - Bizzy-Flash спрашивает Bizzy-Reasoning: "дай стратегический анализ по этим данным, я передам пользователю"

3. **Цикл обратной связи (п. 5) — ключевой, но сложный.** Bizzy должен помнить, что он советовал неделю назад, и иметь данные, чтобы проверить. Это требует:
   - Персистентного хранения рекомендаций с датами
   - Автоматической сверки с текущими метриками
   - Триггера "Bizzy, проверь свои прошлые советы"
   Без этого он будет каждый раз генерировать одно и то же.

4. **У Bizzy нет чувства времени.** Он не знает, что "неделя прошла". Ему нужен внешний триггер — крон или кто-то его пробуждает.

5. **Приоритет — щупальце #2.** Без прямого доступа к данным Bizzy останется пересказчиком. С ним — Bizzy может сам решать: "а дай-ка я посмотрю, что у @qachanell было в понедельник". Это кардинально меняет качество его ответов.

### Итоговая оценка: 8/10

План реален. Риски не в архитектуре, а в модели (DeepSeek Flash может не дотянуть до нужной глубины анализа) и в человеческом факторе (Bizzy нужно настраивать, кормить данными, чистить контекст). 

Первые 3 щупальца (категоризатор → SQL-инструменты → трекер) можно сделать за **2-3 рабочих дня**. После них Bizzy уже будет принципиально полезнее, чем сейчас.

## Что НЕ входит в этот план (осознанно)

- Переписывание бота с нуля
- Замена DeepSeek на другую модель
- Миграция SQLite на PostgreSQL
- Полноценный веб-интерфейс
- Автоматическая публикация постов (без подтверждения)
