# Improvement Proposal — blog-analysis agents

## Текущее состояние экосистемы

```
blog-analysis (агенты, сервер 217.144.185.210)
 ├── SCOUT          → разведка конкурентов (rule-based)
 ├── ANALYST        → контент-аналитика (rule-based, регулярки)
 ├── EDUCATOR       → генерация материалов (шаблоны)
 ├── DIGEST         → дайджест + email (собирает всё в кучу)
 ├── BSA            → DeepSeek-чат с function calling (монолит)
 ├── Orchestrator   → Content Manager + Gateway + PM Agent
 └── requests_listener → Obsidian → BSA

Продукты (Timeweb):
 ├── v0-test-api      → Node/JS + PostgreSQL (платный)
 ├── free-trial-api   → Node/JS + PostgreSQL (бесплатный)
 └── api-practicum-bot → Python/aiogram + SQLite (воронка)

Obsidian vault    → контент-план + общение с BSA через inbox/outbox
```

---

## 1. Надёжность (P0)

### 1.1 Нет мониторинга пайплайна
- `nightly.sh` не проверяет exit-коды предыдущих шагов
- Если SCOUT упал → DIGEST работает без данных → пустой дайджест уходит в email
- Узнать о падении можно только зайдя на сервер и глянув `nightly.log`

**Решение:**
- Telegram-нотификация после каждого nightly run (статус каждого агента)
- Healthcheck-скрипт, проверяющий: сервера доступны, ключи валидны, агенты живы

### 1.2 Lock-файлы без защиты
- `requests_listener.lock` не удаляется при аварийном завершении (kill -9, crash)
- Следующий запуск просто пропускает всё — система замолкает навсегда

**Решение:** обработчик сигналов (`signal.SIGTERM`, `signal.SIGINT`) с гарантированной очисткой

### 1.3 Нет изоляции окружения
- Все агенты в системном Python
- Конфликт зависимостей между агентами сломает всю систему

**Решение:** venv + `requirements.txt` для каждой группы агентов

### 1.4 Каскад без защиты
```
SCOUT падает → нет данных для DIGEST → DIGEST молча делает свою работу → 
пользователь получает пустой дайджест → думает что всё ок
```

**Решение:** каждый агент записывает `status.json` с exit-кодом и ошибкой. Следующий агент проверяет зависимость. Пайплайн шлёт статус.

### 1.5 Жёсткие пути
- `/root/blog-analysis/`, `/root/obsidian-vault/` хардкодом в каждом файле
- Перенос на другой сервер требует тотального рефакторинга

**Решение:** единый `config.yaml` в корне проекта

## 2. Эффективность (P1)

### 2.1 Rule-based вместо LLM
- ANALYST считает посты по ключевым словам (категоризация примитивная)
- SCOUT ищет пересечения по словам, не понимает суть
- Нет тонального анализа, нет выявления трендов, нет креатива

**Решение:** добавить LLM-вызовы в ANALYST и SCOUT. DeepSeek уже есть и стоит копейки.

### 2.2 Файловая система как шина
- Агенты общаются через JSON/MD файлы
- Нет гарантии: файл дописан, не битый, актуален
- Нет версионирования данных между агентами

**Решение:** лёгкая очередь (SQLite job-таблица или Redis если появится)

### 2.3 Нет общего контекста
- Каждый запуск агента начинается с нуля
- ANALYST не знает что нашёл SCOUT
- BSA не знает что написал DIGEST
- Нет cross-reference между инсайтами агентов

**Решение:** shared state — SQLite-база с отчётами агентов, к которой все имеют доступ

### 2.4 Дублирование кода
- Парсинг markdown-секций — в 3+ файлах
- Чтение файлов с одинаковыми паттернами
- Обработка ошибок — у всех по-разному

**Решение:** агентский SDK — общие функции в `lib/agent_base.py`

## 3. Архитектура агентов (P2)

### 3.1 BSA-монолит
- `bsa_agent.py` — 36K строк
- `bsa_chat.py` — 26K строк
- В одном файле: стратегия, контент, dev-операции, email, Instagram

**Решение:** разбить на модули: `strategy/`, `content/`, `devops/`, `email/`

### 3.2 Гранулярность размыта
- BSA делает всё, а ANALYST — только подсчёт категорий
- Content Manager дублирует логику DIGEST
- Orchestrator = три разных агента в одном

**Решение:** аудит ответственности каждого агента, удаление дублирования

### 3.3 Нет API-слоя между агентами
- Вызов агента = `subprocess.run(['python3', 'path/to/agent.py'])`
- Нет таймаутов, retry, graceful shutdown

**Решение:** единый runtime `agent run <name>` с управлением жизненным циклом

---

## 4. Инфраструктура (P0/P1)

### 4.1 Нет CI/CD
- Код пишется на маке → git push → server pull
- Нет тестов перед деплоем
- Нет rollback при падении

**Решение:** минимальный GitHub Action — `git pull && python3 -m venv && pip install -r requirements.txt`

### 4.2 Нет мониторинга продуктов
- free-trial-api может лежать (был Postgres auth failure)
- api-practicum-bot может отвалиться
- Мастер-план упоминает эти проблемы, но агенты о них не знают

**Решение:** healthcheck endpoint на каждом сервисе, агент DEV проверяет их каждый час
